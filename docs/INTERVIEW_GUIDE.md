# GujinBridge 简历与面试说明

## 简历项目描述

**GujinBridge：基于 Qwen3-1.7B 的古文翻译与断句后训练项目**

- 构建覆盖古译今、今译古、古文标点的领域数据流水线，对 9.8 万条样本完成规则审计、人工复核、
  1,024-token 检查及按典籍来源隔离切分，避免训练/测试来源泄漏。
- 使用 LoRA 完成 SFT 与 DPO 后训练；构造 472 条高质量偏好对，使 1,440 条冻结测试集总体字符 F1
  从 72.69% 提升至 73.39%，标点原文保留率从 64.54% 提升至 71.19%。
- 为标点任务实现 GRPO 可验证奖励，设计原文硬约束、标点边界 F1 和位置 F1；通过两轮奖励消融发现
  稀疏/常量奖励失效，并以 checkpoint A/B 与 bootstrap 置信区间拒绝未超过 DPO 的模型。
- 实现 PowerShell 单卡训练、Smoke Test、断点续训、多级 LoRA 重建、批量推理、错误分析和任务专用
  评测工具，形成可复现的 SFT -> DPO -> GRPO 实验闭环。

如果简历空间较小，可保留前三条。

## 90 秒项目介绍

我把 MedicalGPT 的通用训练框架改造成了一个古文领域项目 GujinBridge，基座是 Qwen3-1.7B。项目不只是
换数据：我先建立了古译今、今译古和古文标点三类任务的数据流水线，按典籍来源做隔离切分，并对正文一致
性、标点质量和异常长度做审计，最终得到约 9.6 万条训练数据和 1,440 条冻结测试数据。

训练上先做 LoRA SFT，再从模型真实错误和审核修正中构造 472 条偏好对做 DPO。DPO 把总体字符 F1 从
72.69% 提升到 73.39%，标点原文保留率提升了 6.65 个百分点，因此被选为发布模型。之后我又做了定向
SFT 和两轮 GRPO。第一轮 GRPO 暴露出 Exact Reward 恒为零、格式奖励恒为一的问题；第二轮改成原文
硬约束和标点 Boundary-F1 密集奖励，虽然比第一轮改善，但在统一提示词的 361 条标点测试上仍未显著超过
DPO，所以我没有仅凭训练 reward 上升就宣称有效，而是保留 DPO。这一过程让我完整实践了数据治理、
SFT、偏好对齐、在线策略优化、奖励设计、消融实验和模型晋级决策。

## 面试追问

### 为什么 DPO 数据只有 472 条？

偏好数据强调正确排序而不是规模。数据来自模型真实失败、人工审核修正和候选比较，并对三任务做平衡；
低置信度或 chosen/rejected 差异不明确的样本被过滤。实验结果也显示，小规模高质量偏好数据能带来稳定提升。

### 为什么 GRPO 没超过 DPO？

第一版奖励存在稀疏和常量分量，组内候选缺少有效排序信号。第二版修复后改善了 V1，但单参考标点答案具有
多解，训练来源只有 17 个，而且 on-policy 更新会放大局部奖励偏好，因此没有获得跨来源的稳定提升。

### 为什么不用训练 loss 选择模型？

训练 loss、DPO margin 和 GRPO reward 衡量的是训练目标，不一定与真实下游质量一致。项目用冻结测试集、
一致提示词、逐任务指标、逐样本胜负和 bootstrap 区间做模型晋级，避免把目标函数优化误认为产品效果提升。

### 为什么标点任务不能只看字符 F1？

输入和输出共享绝大多数汉字，即使标点位置错误，字符集合 F1 仍可能很高。因此额外实现了标点类型+位置
Boundary-F1、仅位置 F1、正文完全保留率和标点数量误差。

### 如果继续优化，你会做什么？

优先建立多参考标点测试集与盲测人工评分，扩大独立典籍来源，并把奖励校准到人工偏好。确认评测可靠后，
再尝试按难度分层采样、更多有效候选或更大基座，而不是直接增加相同 GRPO 训练步数。
